## Claude Code から使う場合の前提（重要）

**Claude Code は標準の Grep / Read ツールでローカルの Markdown を直接検索・読み込みできる。** メモフォルダを作業ディレクトリにするか、`/add-dir` / `--add-dir` で追加すれば、MCP サーバ無しでも「検索して要約」はできてしまう。

MCP サーバを作る価値が出るのは次のような場合:
- どのプロジェクトで作業中でも、`/add-dir` なしでメモを引きたい（user スコープで登録すれば全プロジェクト共通）
- メモフォルダへのアクセスを「読み取り専用・ルート配下のみ」に限定したい
- フロントマター（タグ・日付）での絞り込みや、意味検索など Grep では難しい検索をしたい
- 学習・記事ネタとして MCP サーバ自体を作りたい

→ キーワード検索だけで良く、上記に当てはまらないなら **MCP 無し（Grep で十分）** が最小コスト。

## Claude Code への登録（決定: `.mcp.json` ＋相対パス）

- リポジトリ直下の `.mcp.json` に stdio サーバとして記述する（project スコープ）
- 相対パスは **Claude Code を起動したディレクトリ（= リポジトリ直下）** 基準で解決される前提
  - `dotnet run --project MarkdownNotesMcp` / `NOTES_ROOT=sample-notes`
  - サーバ側でも `NOTES_ROOT` が相対パスならカレントディレクトリ基準でフルパス化する
- 注意: サブフォルダで `claude` を起動すると相対パスがずれて起動失敗する。必ずリポジトリ直下で起動する
- 初回は project スコープのサーバ承認ダイアログが出る。登録後 `/mcp` で接続状態とツール一覧を確認

## 結論（推奨構成）

- **公式 C# MCP SDK（NuGet: `ModelContextProtocol`）で stdio サーバ**を作る。ローカル用途なので HTTP は不要
- **サーバは「探す・読む」だけ**。要約は Claude 側（クライアントの LLM）がやるので、サーバから Claude API を呼ぶ必要はない
- 数百ファイルなら**最初はインデックス無しの全件スキャン**で十分速い。遅くなったら SQLite FTS5 に差し替え

## ツール設計（最小 3 本）

| ツール | 入力 | 返すもの |
|---|---|---|
| `search_notes` | `query`, `limit`(既定 10) | パス・タイトル・更新日・マッチ箇所の前後数行（スニペット） |
| `read_note` | `path` | 本文全体（長すぎる場合は先頭 N 文字＋切り詰めた旨） |
| `list_notes` | `folder?`, `since?` | パス・タイトル・更新日の一覧 |

ポイント:
- `search_notes` は**本文を丸ごと返さない**。スニペットで候補を出し、Claude が必要なものだけ `read_note` する 2 段構え。コンテキストを食いつぶさないため
- ツールの `Description` は丁寧に書く（Claude がいつ・どう使うかはここで決まる）
- 「要約して」は Claude が search → read → 要約 を自分で組み立てる。`summarize` ツールは作らない

## 構成

```
MarkdownNotesMcp/
  Program.cs            // Host 構築、stdio トランスポート登録
  Tools/NoteTools.cs    // [McpServerToolType] の 3 ツール
  Services/NoteStore.cs // ファイル列挙・読み込み・検索（ここを差し替え可能に）
  Services/PathGuard.cs // ルート外アクセス防止
```

- `NoteStore` をインターフェース化しておけば、全件スキャン → FTS5 → ベクトル検索 と段階的に入れ替えられる
- ルートフォルダは環境変数 or 引数で渡す（クライアント設定の `env` / `args`）

## 検索方式の段階

1. **全件スキャン（初期）**: 起動時 or 都度 `Directory.EnumerateFiles("*.md")` → `Contains`（大文字小文字無視）。複数語は AND。数百ファイルなら数十 ms 程度
2. **SQLite FTS5**: ファイル数が増えた／遅い場合。日本語は分かち書きが無いので `trigram` トークナイザを使う（2 文字以下の語はヒットしない点に注意）
> Q: trigramとは？
>
> A: 文章を**3 文字ずつずらして切り出した断片**を索引に登録する方式です。
> 例: 「理解負債」→「理解負」「解負債」
>
> - **なぜ使うか**: FTS5 の標準トークナイザは空白で単語を区切ります。日本語は単語の間に空白が無いので、文全体が 1 語扱いになり、ほぼヒットしません。trigram なら辞書なしで部分一致検索ができます
> - **弱点**: 検索語が 3 文字以上でないと索引を使えません（「負債」のような 2 文字語はヒットしない）。また、索引サイズが大きくなります（数百ファイルなら問題になりません）
> - **2 文字語の回避策**: 2 文字以下のときだけ `LIKE '%負債%'` で全件検索に切り替えます。数百ファイルならこれでも十分速いです
> - 別案として、形態素解析（MeCab など）で単語に分ける方法もあります。ただし辞書の用意が必要で、C# からの導入も手間がかかるので、今回の規模には過剰です
3. **ベクトル検索**: 「言い回しが違っても意味で探したい」場合のみ。埋め込みモデルが別途必要で複雑度が跳ね上がるので、必要性が確定してから

## 注意点（必ず押さえる）

- **パス・トラバーサル対策**: `read_note` に `..\..\Windows\...` 等を渡されても、正規化後のフルパスがルート配下か検証する。ルート外は拒否
- **stdout に何も書かない**: stdio トランスポートは stdout が JSON-RPC 通信路。`Console.WriteLine` やログを stdout に出すと壊れる。ログは stderr へ
- **OneDrive のオンデマンドファイル**: 「クラウドのみ」状態のファイルは読み込み時にダウンロードが走り遅い／失敗することがある。対象フォルダは「常にこのデバイスに保持」推奨
- **文字コード**: 基本 UTF-8。古いメモに Shift_JIS が混ざるなら判定が必要
- SDK はバージョンで API が変わりやすいので、実装時に最新の README を確認する

- `MarkdownNotesMcp/`（net10.0、`ModelContextProtocol` 2.4.0）で 3 ツール実装済み。すべて `ReadOnly = true`
- stdio で手動テスト済み: 検索・読込・一覧、`../` や絶対パスの拒否、日付絞り込み
- 実装中に入れた対処
